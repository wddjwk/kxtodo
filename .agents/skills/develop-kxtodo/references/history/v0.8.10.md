# v0.8.10 剪切板同步重构 + 无响应整治 + AppImage 标准路径

> 这一版是 **v0.8.9 剪切板同步的返工**：先修「发现第一台设备就整机无响应」的死锁，再把配对模型从「共享口令」换成用户要求的「局域网全量发现 + 广域网账户 + 每设备勾选」，同时把界面改成开关 + ⓘ 说明、按 360 窄屏重排；应用侧修 Linux AppImage 在 Wayland 下无响应/卡顿的非标准后端选择。**没有新增账户体系**：统一服务器复用 kxtodo-server 的现有账户（用户名 + 密码 → auth_key）。

## 一、无响应与卡死（最优先）

### 1.1 根因链条

1. **服务内自锁**：`Inner::push_peer` 在持有 `lan_peers` 的 `std::sync::Mutex` 时调用 `emit_status()`；`status_snapshot()` → `peer_list()` 再次锁同一个 `lan_peers`。std Mutex 不可重入 → 后台发现线程永久卡住。**只要局域网里出现第一台开启剪切板的设备就触发**，这就是「同一个 WiFi 两台设备互相发现不了」和「点刷新必现卡死」的共同根因：发现循环死在回包之前，状态查询再去抢同一把锁。
2. **主线程放大器**：`clipboard_status` 当时是**同步 Tauri 命令**，同步命令跑在主线程上。后台锁一被卡住，前端每 3 秒的状态轮询/刷新按钮就把主线程也挂死 → 窗口「未响应」，系统问是否 force quit；桌面隐藏到托盘后的重启也会去碰同一个卡死的实例，看起来像「退出重启也卡死」。
3. **状态快照的锁纪律**：同一个函数里多处 `if let Ok(guard) = mutex.lock()`，若未来在持锁期间调用网络/IO，同样会卡。现在统一改成「克隆 → 放锁 → 拼 JSON」，并在 `emit_status` 里序列化后与上一次比较，只有变化才发事件。
4. **v0.8.10 的防护**：`clipboard_status` / `clipboard_refresh` 都是 `async fn` + `spawn_blocking`；新增回归 `status_after_new_lan_peer_does_not_self_deadlock`（用线程 + 3 秒超时，死锁会直接失败）。

### 1.2 局域网发现（真实两台机器验证）

- **发送**：UDP `52178` 同时发 `255.255.255.255:52178`、每张网卡的子网广播（`if-addrs` 读 `broadcast`/netmask 计算）和组播 `239.255.77.53`。Windows 上组播按每个本机 IPv4 逐个 `join_multicast_v4`，失败不致命（广播是主路径）。
- **接收**：解析后按 `deviceId` 合并；新设备**单播回一包**到来源（AP 隔离/防火墙常挡广播，反向单播通常能通）。发现包不含口令，只含设备 id/名字/TCP 端口。
- **绑定**：UDP 用 `socket2` 建 socket，`SO_REUSEADDR` + `SO_BROADCAST` + 非阻塞，再交给 tokio；TCP 先重试默认 `52179` 五次（120ms），失败退临时端口。广播里带**实际** TCP 端口，所以临时端口也能被连。
- **端口覆盖**：`KXTODO_CLIPBOARD_DISCOVERY_PORT` / `KXTODO_CLIPBOARD_LAN_PORT` 只给探针/同机多实例；正常应用不设，仍是 52178/52179。加这个是因为开发机上的旧版应用占着固定端口，探针无法绑定；同时也是以后排查「端口被谁占了」的入口。
- **探针**：`src-tauri/crates/core/examples/clipboard_probe.rs` 无界面跑同一份 core，打印每秒状态 JSON；不读写系统剪贴板，可安全跨机跑。用法见文件头。
- **实测**（Windows 192.168.31.144 ↔ kklaptop 192.168.31.102，同一 WiFi）：
  - 诊断端口 53178/53179：双向都发现 `transports:["lan"]`。
  - 停掉旧应用、固定 52178/52179：双向都发现，TCP 端口 52179。
  - 统一服务器（kklaptop 上 `kxtodo-server --listen 0.0.0.0:52277`，两端同 account/password，探针 `--no-lan --server ...`）：双向 `transports:["server"]`、`serverRegistered:true`。
  - P2P（探针 `--no-lan --p2p --account ... --password ...`）：双向 `transports:["p2p"]`，名字正确。

### 1.3 P2P 名字记录踩到的坑

v0.8.10 初版把设备名记录也用**房间私钥**签（`directory::publish_name(&client, &room, ...)`）。pkarr 的一个 key 只有一份包，`_name` 与房间目录的 `_kxtodo` 是**同一个 key 的两组 TXT**——发名字等于把整个房间设备目录覆盖掉。症状极具误导性：Windows 看得见 Linux、Linux 看不见 Windows（谁的 `_name` 后发谁就把对方抹掉），且两端都显示「未命名设备」。修法：名字记录永远用**设备私钥**签，`fetch_name(device_id)` 才对得上；房间私钥只用于房间目录。

## 二、配对模型重构

### 2.1 设置（`ClipboardSettings`，全部本机偏好，不进同步共享子集）

```
enabled / deviceName / lanEnabled /
serverEnabled / wanP2pEnabled / serverUrl / account / password /
types{text,html,image,files} / limits{textMb,htmlMb,imageMb,filesMb} / saveDir
```

- **移除**：`code`、`directEnabled`、`directAddresses`。旧的 `p2pEnabled` 也不再复用：v0.8.9 它是「口令模型的第三路」，新模型里 P2P 属于广域网且需要账户，复用同名会让旧配置里的 `true` 被读成「广域网已开但没账户」，把局域网也拖停（真机测试实际踩到）。新 JSON 名是 `wanP2pEnabled`，旧的 `p2pEnabled` 被 serde 忽略。旧用户只要 `enabled=true && lanEnabled=true` 就会直接开始局域网发现（不写迁移代码）。
- **保存与启动解耦**：`normalize_settings` 不再因为「缺广域网账户/密码/服务器地址」而拒绝保存（旧配置升级、CLI 分步配置都要能用）；服务只启动 LAN / WAN 中条件满足的部分，缺的那块写进状态错误。GUI 的保存按钮仍即时校验。
- `deviceName` 只存前缀：空 → `kxtodo·平台(deviceId 前 8 位)`；非空 → `前缀·平台`。平台由 core 拼。
- `serverUrl` 允许只填 IP：core 在 `normalize_settings` 里补 `http://` 与 `:52177`（显式端口/路径保留）。账户名大小写不敏感（`derive_keys` 已统一）。

### 2.2 每设备勾选

- 存 `runtime/clipboard-selection.json` 的 `disabled: [deviceId]`，空 = 全部勾选。**默认全选**，所以两台设备刚发现就能同步（用户要求「输入账户密码后默认都勾选」）。
- 新命令 `gui.clipboard-peer`（UI-only，不进审计）更新文件并立刻改运行中服务的 `disabled` 集合，**不重启服务**、不写 settings.json。
- 发送时过滤掉未勾选设备；接收端在握手后也检查来源是否被本机勾选，未勾选就拒绝写入。双方都勾选是实际生效条件。
- 界面：局域网区与广域网区各自过滤同一个 `status.peers`，同一设备可能同时出现（勾选是同一个 id）；未勾选行降透明度但保留，能重新勾上。

### 2.3 局域网握手（无共享秘密）

- 设备身份 = `runtime/clipboard-identity.json` 的 Ed25519/iroh 私钥；`deviceId = public.to_z32()`。
- Hello/Ack 各含 `device/name/nonce/eph` 与对 `kxtodo-clipboard/2/{hello|ack}|device|nonce|eph` 的 Ed25519 签名；对方用 `EndpointId::from_z32(device).verify(...)` 验签。
- 每次连接生成临时 X25519 密钥，会话密钥 = `SHA256("kxtodo-clipboard/2/session" + DH + client_nonce + server_nonce + client_device + server_device)`；帧用 ChaCha20-Poly1305，AAD 绑定双 nonce。抓包看不到明文，也无法用旧包重放（临时密钥每连接不同）。
- 握手后所有帧带随机 12 字节 nonce；消息 id 去重 5 分钟（先占位再读、失败撤回）。

### 2.4 广域网

- **统一服务器**：新增 `kxtodo-server` API：
  - `POST /api/v1/clipboard/presence` `{deviceId,name,endpointId,addrs}`（Bearer token；upsert；TTL 90s）。
  - `GET /api/v1/clipboard/peers?deviceId=...`（同账户、未过期、排除自己；返回同样的元数据）。
  - `DELETE /api/v1/clipboard/presence?deviceId=...`（退出时尽力；TTL 兜底）。
  - SQLite 新表 `clipboard_presence(user_id, device_id, name, endpoint_id, addrs, updated_at)`；只做发现，**不存内容**。
  - 客户端 `SyncClient::clipboard_presence/clipboard_peers/clipboard_leave` + `new_with_timeout`（10s）；`server_step` 登录失败会 register 再 login，token 失效重登一次。
  - 服务端每 5 秒拉一次，成功后 `serverRegistered=true`；界面只显示「服务器」徽章，不显示端口/地址。
- **P2P**：`room = SHA256("kxtodo-clipboard/2/room" + lowercase(account) + dir_key)`；发布房间条目（EndpointId + 直连地址）与设备名记录；每 5 秒拉取、名字缓存 30s、条目 60s 过期；ALPN 独立 `kxtodo-clipboard/2`。
- **发送目标**：同一 deviceId 合并 LAN 与 WAN，优先 LAN（更快），失败再走 iroh；两条线路都失败才报错。接收端按消息 id 去重兜底。

### 2.5 设置与状态

- 服务签名包含 config + relay/directory，设置一变就停旧起新；`stop()` 用 `notify_waiters + notify_one` 避免重试窗口丢唤醒。
- 状态新增 `serverRegistered` / `p2pActive` / `peers[].selected`；移除 `codeReady` / `preferred` / `online`。
- 错误分槽（send / lan / endpoint / server / p2p），状态里取第一条非空，避免某个子系统恢复后旧错误一直挂着。

## 五、AppImage 无响应与卡顿

- **根因不是 AppImage 格式，而是我们改了标准路径**：linuxdeploy 的 AppRun 为绕 tauri#8541 强制 `GDK_BACKEND=x11`。v0.8.9 为 WSLg 的光标问题，在**所有** `APPDIR + WAYLAND_DISPLAY` 会话里把这个强制值删掉，Ubuntu/GNOME 上回退到原生 Wayland，出现无响应/卡顿。
- **修法**（`src-tauri/src/lib.rs::prepare_linux_webview`）：
  - 只有 WSLg（`WSL_INTEROP` / `WSL_DISTRO_NAME`）才撤 `GDK_BACKEND=x11`；真实 Linux 桌面保持 AppRun 的 x11。
  - NVIDIA 专有驱动（`/proc/driver/nvidia/version`）默认 `WEBKIT_DISABLE_DMABUF_RENDERER=1`；Wayland 下再设 `__NV_DISABLE_EXPLICIT_SYNC=1`。AMD/Intel 保留 DMA-BUF 快路径。
  - `KXTODO_WEBKIT_SAFE=1` 是非 NVIDIA 的逃生门；用户已显式设置环境变量时不覆盖。
- **构建**：仍是官方 Tauri bundler；CI 在 ubuntu-latest（24.04）构建，AppImage 不打包 glibc，更老发行版需评估。官方建议在更老基底构建；受 WebKitGTK 4.1 可用性限制，本项目的基线写清楚为 24.04。
- 诊断日志：`journalctl --user -b | grep -iE "kxtodo|webkit|egl"`；`KXTODO_WEBKIT_SAFE=1 ./KXToDo.AppImage` 对照；确认 `GDK_BACKEND` 是否为 x11。

## 七、教训

1. **std Mutex 不可重入**：任何 `emit_*` / 通知函数都可能在内部再取同一把锁；锁纪律要写成「持锁只做内存读写」。
2. **状态查询命令默认 async**：Tauri 同步命令在主线程，后台一卡整窗无响应；这不是「刷新按钮」的错。
3. **pkarr 一个 key 一份包**：同一把 key 下的不同 TXT 名会互相覆盖；名字与目录必须用不同密钥。
4. **Android 宽度回归要逐元素量**：页面级 `scrollWidth` 对绝对定位/溢出子元素不敏感。
5. **别用非标准环境变量覆盖成熟打包器的默认值**：AppRun 的 `GDK_BACKEND=x11` 是 Tauri 的稳定路径，WSLg 例外要精确到 WSLg。
