## 这一版的主题

v0.8.0 **没有新功能**，是一次正确性 + 性能 + 卫生版本。三条主线：

- **正确性**：前端单测地基（vitest）建起来后直接挖出 6 个前后端/跨语言同口径 bug（日记写作时刻从来没显示过、32~62 天区间 GUI 与 CLI 分桶不一致、≥39 位金额静默归零、搜一个「,」列出整本账、NaN 字号整页失效、legacy 单图折叠两侧结论相反）；另修 reparent 不落盘（N1）、`Ctrl+Shift+K` 类快捷键静默失效（N7）等。

## 批次 1：写路径去放大（Rust core）

① **history.rs 的追加不再动辄整文件重写**：append 前先判是否需要 trim（`fs::metadata` 体积 + 本次行长），trim 目标从 max_bytes 收到 **80%**——trim 到上限意味着下一条追加又触发整文件重写，把重写成本摊到几千次追加。② **`migrate.rs` 整个删除**（v8→v9 上古迁移，用户确认已无此迁移需求）：连带删 `tests/migration.rs`、`repo.rs` 里 12 处 `migrate_if_needed` 调用、`time.rs::migrate_legacy_local_time`、`exec.rs::split_legacy_arguments`、`tests/common/mod.rs` 的 v8 fixture 助手——「不做兼容」铁律从此**连迁移代码都不留**，别把它加回来。③ **host.rs 去掉每条命令前的 `load_all()` 预检**（写命令自己会 load 相应领域文件，预检是白读一遍盘）；`load_all` 保留给 GUI/APK 启动与 host_scheduler 测试，并补了文档注释说明去处。④ **repo.rs 的审计与备份**：`audit()` 跳过 6 个纯 UI 命令白名单 `UI_ONLY_COMMANDS`（select-node / set-collapsed / set-item-ui / set-items-ui / set-diary-ui / set-schedule-ui——点一下树节点就写一行审计日志，台账会被 UI 噪音灌满）；`backup_locked` 备份**五个**领域文件（原来只备三个，diary/ledger 写坏了没有备份）；损坏提示改成「`backups/` 里有最近 5 份全量备份，手工拷回覆盖即可」——**没有自动恢复命令**（`restore` 与 LWW 语义冲突，见「不做的事」）。⑤ **ops_gui.rs**：模块文档写明「不发域事件」的契约；**N1 正确性修复**——`gui.apply-tree-order` 里跨父移动（reparent）必须算 changed，原来只比 order，**换父级但 order 数值相同时改动被当成「没变」而不落盘**；N15 `set-items-ui` 用 `HashSet<&str>` 替掉 `ids.contains` 的线性扫。⑥ **doctor.rs 的领域文件体检从 3 个扩到 5 个**（补 diary 与 ledger 及各自的 SCHEMA_VERSION）；删掉「运行任意命令触发迁移」的过期提示（迁移已不存在）。⑦ **`is_safe_image_name` 全项目收成一个实现**：`diary_archive.rs` 的这份补上 Windows 保留字符 `<>:"|?*`，`src-tauri/src/lib.rs::safe_image_name` 改成委托它——原来两份实现口径不同。

## 批次 2：渲染去无用功（前端）

① **markdown.ts 的记忆化与早退**：block/inline 两套 LRU（300 条 / 4MB 与 800 条 / 400KB）+ `renderStats` 计数挂 `window.__kxtodoRenderStats`（perf-bench 靠它断言「首屏 block 渲染为 0」）；`restoreMath`/`restoreCode` 改单趟正则替换（原来逐段循环）；`highlightCodeBlocks`（`!html.includes("<pre")` 早退）/`transformDiagrams`/`transformCodeBlocks` 都加早退；`DIAGRAM_PATTERN` 提到模块级——原来每次调用都重编译一遍正则。② **`measureBus.ts`（新）**：全应用共享**一个 ResizeObserver + 一个 window resize 监听 + rAF 合帧**，导出 `observeResize(element, listener): () => void`；RO 的条目只通知受影响的元素，window resize 通知全部。原来每张卡片自己 new 一个 RO 再各挂一个 window resize。③ **TaskCard / DiaryCard 的 `fullHtml` 只在展开时渲染**（`$: fullHtml = isExpanded ? renderMarkdown(...) : ""`）：**Svelte 的 `$:` 是急切求值，与模板消不消费无关**——折叠态卡片原来也白跑一遍完整 markdown 渲染（12 步，含 DOMPurify 的完整 DOM 解析），一屏 300 张折叠卡就是 300 次白渲染，且每次列表变化都重来。`resolvedMd` 仍照旧 eagerly 算（它负责触发插图预加载）。两个组件的测量都改用 `observeResize`。④ **Workspace.svelte 的 `measuredExpandable` 从数组改 `Set<string>`**：`handleCardMeasure` 先判 `has` 再 add/delete，然后 `measuredExpandable = measuredExpandable` 自赋值失效——**Svelte 的失效基于赋值，Set 原地改不会触发**。⑤ **stores.ts**：`appliedRevisions: Map<string,number>` + `noteRevisions()`，`listenCoreEvents` 在 `(appliedRevisions.get(domain) ?? 0) >= revision` 时跳过旧事件；`applySnapshot` 每个分支加 `&& snapshot.X !== undefined` 守卫——**按域拉取时缺的域不能被当成空**；`refreshFromCore` 在清空 pending 之前先捕获 `wanted` 再传给 `coreSnapshot(wanted)`（只拉脏域）；`hydrate()` 把 getAppVersion + hasCoreDispatch + event 模块动态 import 并行化；新增 **`debouncedSearchQuery`**（180ms 防抖，空串立即生效、首次发射直通），`visibleTasks`/`isSearching`/`searchHits` 全部消费防抖值——每敲一个键全量混排搜索是交互耗时大头。⑥ **backend.ts**：`CoreSnapshot` 字段全部改可选、`revisions?: Partial<Record<...>>`、`coreSnapshot(domains?: readonly string[])`。⑦ **syncRunner.ts**：`FIRST_ROUND_DELAY_MS = 1200`，`boot()` 结尾 `arm(1200)` 而不是立刻 `tick()`——首轮同步不和水合抢主线程。⑧ **actions.ts**：`saveTaskMarkdown` 先算 `expandChanged` 再乐观更新，只在展开态真变了才发 `gui.set-item-ui`（原来每次保存都白发一条）；`setItemsUi` 用 `new Set(ids)`。⑨ **images.ts**：`boundedPut(cache, key, url, budget)` 给三个 dataURL 缓存加体积上限（md 64MB / background 32MB / avatar 8MB）。⑩ **lib.rs（Tauri 壳）**：`core_snapshot(core, domains: Option<Vec<String>>)` + `wanted(name)` 闭包 + `put_snapshot_domain` 助手（从序列化结果的 `_meta.revision` 读版本号）；**N7 修复**——`shortcut_from_string` 重写 + 新 `key_code(token)`，覆盖 a-z / 0-9 / F1-F24 / 方向键 / space,enter,esc,tab,backspace,delete,insert,home,end,pageup,pagedown 与标点：旧实现认不出的 token 被**悄悄丢掉**，于是 **`Ctrl+Shift+K` 这类快捷键注册成功但永远不触发**。

引入 **vitest 5**：独立 `vitest.config.ts`（**刻意不复用 vite.config.ts**——vitest 的 CONFIG_NAMES 是「找到第一个就用」，独立文件就完全避开 svelte 插件、`optimizeDeps.include:["mermaid"]` 与 rollupOptions）；environment = `node`，**不装 jsdom/happy-dom**（`defaults.ts` 顶层调 plugin-os 的 `platform()` 会抛 ReferenceError，正好被它自己的 try/catch 接住回落到 `navigator.userAgent`，node 环境因此跑得通）；`package.json` 加 `test:unit`；ci.yml 的 frontend job 在 `npm run check` 之后、`npm run build` 之前插一步。三个 spec：`src/lib/__tests__/{ledger,clock,defaults}.spec.ts` 共 124 用例，**五个时区（UTC / New_York / Berlin / Shanghai / Kiritimati）全绿**——断言一律用 `todayDate()`/`shiftDays()` 相对构造或无时区时间戳（**断言必须时区无关**：CI 的 ubuntu 是 UTC，开发机是 UTC+8）。

### 由这些单测挖出、并在本版修掉的 6 个正确性问题（本批次最主要的产出）

① **`clock.ts::clockOf` 对真实落盘的两种 createdAt 一律返回空串**：它按 `timestamp.slice(11)` 字面切片再交给带尾锚的 `parseClock`，而 `new Date().toISOString()` / core `now_iso()` 写的是 `"…T04:20:41.693Z"`、core `diary_archive::compose_timestamp` 写的是 `"…T12:20:00+08:00"`，两种尾巴都被拒。后果：**日记的写作时刻在编辑器与卡片菜单里从来不显示**（开发机 diary.json 里 7 篇没有一篇能解析），且 `actions.ts::applyDiaryChanges` 因此把本地 `createdAt` 重写成裸日期、丢掉整个时钟部分（浏览器 legacy 路径会持久化）。修法是改用 `new Date()` 解析 + 本地 `getHours/getMinutes`，与 core 的 `time_of`（`parse_from_rfc3339` 后转 Local）同口径，**顺带修掉时区错**——字面切片对 Z 时间戳给出的是 UTC 钟点，东八区差 8 小时。长度 <11 的门槛保留：裸日期会被 Date 按 UTC 解析，放进来就错了。② **统计分桶门槛两侧不同**：前端 `ledger.ts::bucketOf` 是 `days <= 62`，core 是「from 与 to 落在同一个自然月」→ 32~62 天的自定义区间 GUI 画日桶、CLI 给月桶。统一到 **62**（core 侧新增 `DAY_GRAIN_MAX_DAYS`），并加一条 `include_str!("../../../../src/lib/ledger.ts")` 的测试把前端那个数字读出来与常量比对（与 `tests/ledger_icons.rs` 同一路数）——**光靠注释说「两边要一致」一定会漂**。③ **core `parse_cents` 对 ≥39 位整数部分 `.unwrap_or(0)` 静默归零**：i128 装不下就当成 0，于是「四十位数字的 `--initial`」被写成 0。`ledger add` 有 `amount_cents <= 0` 的写入门兜住（只是报错误导），而 **`account-modify --initial/--balance` 里 0 是合法值，会真的把期初写成 0**。修法是空串（全是前导零）才给 0、否则 `.ok()?` 拒绝，中间步骤全部换 checked 算术——37 位时 ×100 溢出也要拒，不是 debug 下 panic。④ **`filterLedgerEntries` 两个洞**：只由逗号/空格组成的查询会让 `amountNeedle` 变成空串，而 `String.includes("")` 恒真 → **搜一个「,」把整本账都列出来**；`amountCents` 恒为正所以**带符号的查询永远搜不到**，而界面上支出明明画着 `-12.34`。修法：`amountNeedle` 为空直接不匹配金额；按 kind 补一份带符号形态（支出 `-`、收入 `+`、转账不带符号，与 `LedgerEntryRow::amountText` 一致）。⑤ **`defaults.ts::normalizeFontSize` 缺 `Number.isFinite` 守卫**：NaN 一路穿过去变成 `--font-ledger: NaNpx`，**整页字号失效**。同文件的 `normalizeUiScale` 与两个整数归一都判了，只有这个漏。JSON 里存不下 NaN，但设置对象也会由 localStorage 的外观缓存与 NumberField 的输入拼出来，洞是可达的。⑥ **`normalizeLedgerEntry` 的 legacy 单图折叠判据与 core 相反**：前端拿 `Array.isArray(item.images)` 当分支条件，core 拿 `images.is_empty()`，于是 `"images": []` 配上旧 `image` 时**前端丢图、core 保留**——同一份 JSON 两侧结论相反。修法是前端也按「原始数组为空」判分支（过滤后的结果不当判据）。

`meta.nextCursor` 双写**；`render.rs::render_pretty` 的兜底分支原来是 `_ => return render_kv(data)` **提前返回**，永远走不到合计行，改成键值输出后再补一行「共 N 条」——命中的只有 ledger.list 与 diary.list（其它命令都有专属渲染器）。⑤ **`diary list` 的 `data.total` 改成过滤后的篇数**（原来是 `file.entries.len()`，即全库篇数）：`diary list --from 月初 --to 月末 --jq .data.total`（「这个月写了几篇」）原来报的是全库篇数；现在与 ledger list 同口径，`total` 与 `returned` 并排 = 「命中 N 篇、本页 M 篇」。⑥ **jq.rs 补两块语法**：`{a, b}` 对象构造（`{a}`/`{.a.b}` 简写，键取路径最后一段；`{"名字": .a.b}` 显式键，裸标识符或单/双引号；`{}` 空对象；某字段产出多值时按 jq 语义做笛卡尔积；键顺序 = 写下的顺序）与 `.a, .b` 逗号多输出。程序模型从 `Vec<Stage>` 改成 `Vec<Segment>`（`Segment = Vec<Stage>`）：**先按 `|` 切段、段内再按 `,` 切分支**——jq 里 `,` 优先级高于 `|`。`split_top_level` 现在也跟踪 `{}`/`[]` 深度。顺带**修好 `.[]`**：`JQ_SUBSET_DOC` 一直写着支持 `.a[] 或 .[]`，实现却在 `.` 后遇到 `[` 就报「`.` 后必须是字段名」。语法错误的 hint 从「支持范围见 schema jq」改成**内联整条支持清单**（`SUPPORT_SUMMARY` 常量）——调用方不必再跑一次 `schema jq`，那条往返在自动化里就是白烧一轮；有测试同时断言 hint 与 `JQ_SUBSET_DOC` 都含新语法，防两边再漂。⑦ **render.rs：`--jq` 生效时 `--format` 没有落点，但不静默丢**——非 json 时在 **stderr** 出一行提示（stdout 必须保持可被脚本解析的纯 JSON，多一个字符就炸）；jq **失败**路径刻意不拼提示（那时 stderr 是错误信封，调用方要解析它）。新增 `Format::as_str()`。⑧ **help 补 clap 的 `default_value`**：`task list`/`task find`/`schedule list`/`schedule find` = 50、`schedule logs` = 20（core 里本来就有这个真实默认，`unwrap_or(20)`），补上后 `--help` 与 `schema` 都能机读默认值、行为不变；**`ledger list` / `diary list` 的 `--limit` 刻意不加**（它们没有默认值 = 返回全部）。`--cursor` 的帮助文案统一成「分页游标（取上一页 meta.nextCursor）」、`--all` 统一成「输出全部（忽略分页）」。

## 批次 6：体积与占用

① **APK 砍掉 x86 / x86_64，只留 `aarch64-linux-android` + `armv7-linux-androideabi`**：`scripts/package.ps1`（`rustup target add` 两个 + `npx tauri android build --apk --target aarch64 --target armv7`）与 `.github/workflows/release.yml`（`targets:` 两个 + 同样的 build 命令）都改；产物收集加**分档兜底**（`universal/` → `arm64-v8a/` → 最新的那个）——给了显式 `--target` 后 gradle 可能不再产出 universal APK，而「最新的那个」会在两个 ABI 之间摇摆，只当最后兜底。理由：x86/x86_64 纯为模拟器服务却占掉 APK 一半体积（实测 71.5MB 里 35.4MB 是这两个 ABI 的 .so），而移动端回归验证走 Playwright + 系统 Edge，不依赖 x86 APK。**armv7 刻意保留**（真机覆盖面）。② **`src-tauri/Cargo.toml` 加 `[profile.release]`**：`lto = "thin"` / `codegen-units = 1` / `strip = true`（cargo 默认无 LTO + 16 codegen units + 不 strip；预计全线 -25~35%，代价是编译时间明显变长），并带注释**禁止加 `panic = "abort"`**——GUI 是常驻 Host，调度器用 process_group/killpg 管整组子进程，让一次 panic 直接带走整个常驻进程比 unwind 到边界更糟；Android 的 cdylib 上 abort 也不友好。③ **图片入库体积闸 `src-tauri/src/lib.rs::shrink_oversized_image`**：**只在超过 5MB 时动手**（小图重新编码只有看不见的损失、没有收益）。JPEG（多半是手机原图，实测有 19MB 的列表背景）长边收到 2560、质量 90；PNG（多半是票据与长截图，以文字为主）长边上限放宽到 4096、仍然无损编码——宁可省得少也不糊字；**其它格式一律原样保留**（GIF/WebP 可能是动图，解码只拿得到第一帧，重编码等于把动画弄丢）。三条兜底任何一条不满足都原样返回：解码失败、重编码失败、重编码后反而没变小——**压缩永远不许弄丢或弄坏用户的图**。API 坑：`image` 0.25 的 `PngEncoder` **没有** inherent `encode`，两个编码器都要走 `ImageEncoder::write_image(self, buf, w, h, ExtendedColorType)`。5 个图片命令（`save_background_image`/`import_background_image`/`save_avatar_image`/`save_md_image`/`save_md_image_data`）改成 `async fn` + `tauri::async_runtime::spawn_blocking`——Tauri 的同步命令跑在主线程上，一次几十 MB 的解码+缩放就能把窗口和 IPC 卡死。新增 `image = { version = "0.25", default-features = false, features = ["jpeg","png"] }`。④ **`vite.config.ts` 加 `build.rollupOptions.output.manualChunks`**：把 `node_modules/katex/` 拆成独立 chunk——公式渲染只在预览里用，不该压在首屏 chunk 里。

## 明确决定不做的（连同理由，这些也是结论）

- **实体级增量快照与虚拟滚动**：改动面大、在真实数据量（几百条）下收益不明显，且容易引入正确性问题。
- **CSS `contain: paint` / `content-visibility`**：`contain:paint` 会裁掉 TaskCard 的日期浮层；`content-visibility` 会让 `scrollHeight` 量不出真实高度，而折叠/省略号判定就靠它。
- **存储分片（把 ledger.json 按月拆）与记账列表的月份窗口化**：真实账本量级不到需要分片的程度。
- **墓碑 GC**：有复活风险（本地更新可以复活墓碑）。
- **`restore` 命令**：与 LWW 语义冲突（恢复靠手工从 `backups/` 拷回覆盖）。
- **服务端图片删除传播**：服务器只持有密文，无从判断引用。
- **`lib.rs` / `SettingsDrawer.svelte` 拆分、diary.css 与 ledger.css 合并、模块循环依赖清除**：纯结构整理，风险大于收益。
- **`formatCents` 对非整数入参的取整不对称、core `parse_clock` 收 `+9:+5`、`normalizeLedgerEntry` 放行 `2026-13-45` 这类非法日期、`seedLedgerBook` 的 `createdAt` 让两次调用不 deep-equal**：都不可达或无害。
- **删掉 `tauri-plugin-opener`**：查过，它确实在用。

## 新增的验证手段

**`scripts/perf-bench.mjs`（新）**：往 localStorage 塞 300 任务 / 300 日记 / 3000 账目（键 `todo-note-state-v3` / `todo-note-diary-v1` / `todo-note-ledger-v1`），量冷启动、**页内 rAF 计时**的交互——Node 侧计时会被自己的 `waitForTimeout` 淹没（实测过一次搜索 272ms 里 260ms 是脚本自己的 sleep），并断言 `window.__kxtodoRenderStats`（**首屏 block 渲染必须是 0**）。需要 `npm run dev` 起着。

实测数字（开发机，改后）：首屏 DOM 里 257 张卡片而 `block=0`（改前是 257，即每张折叠卡都白渲染一遍）；勾选一条任务 12-13ms、展开一张长卡 16ms、记账列表换月 13-14ms、切统计视图 21-25ms、搜索按键→结果 ~197ms（其中 180ms 是刻意的防抖）；inline 记忆化命中率 4068/4325 ≈ 94%。
